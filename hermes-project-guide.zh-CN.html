1. 项目介绍

Hermes 是 Nous Research 开源的自进化 AI Agent。它将模型调用、工具执行、长期记忆、技能、定时任务和多端会话整合到同一代理核心中；用户可以在本地终端、TUI、桌面应用，或 Telegram、Discord、Slack、WhatsApp、Signal 等消息渠道与同一类 Agent 交互。

多入口交互

经典 CLI、Ink TUI、消息网关、Web Dashboard 与 Electron Desktop 共用后端能力和会话体系。

工具与环境

工具通过注册表自动发现，按 toolset 启用；可运行在本地、Docker、SSH、Daytona、Singularity、Modal 等终端环境。

学习与持久化

技能、记忆和 FTS5 会话搜索支持跨会话积累；复杂任务可委派给隔离子 Agent 并支持 cron 自动化。

模型与扩展

支持 OpenAI、Nous Portal、OpenRouter 及自定义端点等；提供 MCP、插件和可选依赖，避免将所有能力固化进核心。

适合的落地场景：企业/个人知识助理、IM 机器人、研发自动化、定时巡检与报告、私有化多模型 Agent，以及围绕特定业务系统构建的插件化助手。

3. 本地复现步骤

以下路径用于从源码启动一个可交互的最小 Hermes 实例。模型服务凭据属于敏感信息，应只写入 ~/.hermes/.env；其它行为配置使用 ~/.hermes/config.yaml 或设置向导。

3.1 前置条件

  • Git、Python 3.11–3.13、Node.js 22.22 / 24.11 / 26+ 与 npm。
  • 一个可用的模型提供商账号或兼容 OpenAI 的 API 端点。
  • 可选：Docker Desktop（容器化复现）、一个消息平台 Bot 凭据（网关复现）。

3.2 建立 Python 开发环境

git clone https://github.com/NousResearch/hermes-agent.git
cd hermes-agent

# 安装 uv（若系统尚未安装）
curl -LsSf https://astral.sh/uv/install.sh | sh

# 创建并安装完整开发依赖
uv venv .venv --python 3.11
source .venv/bin/activate
uv pip install -e ".[all,dev]"

3.3 配置并验证最小对话

# 通过交互向导选择模型提供商、填写 API Key、设置默认模型
hermes setup

# 或只进入模型选择流程
hermes model

# 启动经典 CLI；输入“你好，请说明你能做什么”进行验证
hermes

# 可选：运行诊断
hermes doctor
配置边界：不要将 API Key、Token 或密码提交到仓库；不要为普通开关新增 HERMES_* 环境变量。非密钥配置应落在 config.yaml。

3.4 启动 TUI、Web 与桌面端

# 在仓库根目录安装 JS 工作区依赖
npm install

# TUI：构建并启动
npm run build --workspace ui-tui
hermes --tui

# Web Dashboard：构建前端后启动本地仪表盘
npm run build --workspace web
hermes dashboard --host 127.0.0.1

# Desktop（可选，开发模式）
npm run dev --workspace apps/desktop

3.5 消息网关与容器化复现（可选）

# 先在 hermes setup 或 gateway 设置流程中配置所选平台凭据
hermes gateway setup
hermes gateway start

# Docker：挂载本机 Hermes 数据目录并启动网关和 Dashboard
HERMES_UID=$(id -u) HERMES_GID=$(id -g) docker compose up -d

容器的 Dashboard 默认仅绑定本机回环地址。远程访问建议使用 SSH 隧道或带认证的反向代理，避免以不安全方式直接暴露服务。

5. 二次开发 Plan（插件优先）

建议先确认业务目标（例如：知识库问答、工单助手、业务报表或垂直 IM Bot），随后从最小可用能力迭代。Hermes 的核心原则是保持 Agent 核心与模型工具 schema 稳定：优先扩展已有代码、CLI+Skill、服务门控工具、插件或 MCP，最后才考虑新的核心工具。

阶段 0｜调研与边界（1–2 天）

定义目标用户、接入渠道、模型/预算、数据源、权限与审计要求；选择单一首发入口（建议 CLI 或一个 IM 平台），写出 3–5 条验收场景。

阶段 1｜最小可用 Agent（3–5 天）

完成 provider、默认模型、工作目录、命令审批与会话策略；以真实任务验证工具调用、会话持久化和失败反馈。将提示词、流程说明沉淀为 Skill，而非动态改写系统提示词。

阶段 2｜业务能力接入（1–2 周）

优先制作独立插件或 MCP：封装业务 API、鉴权、输入校验、最小权限与可观测日志。若只需管理配置或后台任务，新增 hermes <subcommand> 配合 Skill，而不是新增模型工具。

阶段 3｜多端与自动化（1 周）

接入一个消息平台，配置用户白名单/配对；用 cron 生成日报、巡检或同步任务。需要 GUI 专属能力时，按会话 platform/toolset 判定可用性，不能依赖后端进程环境变量。

阶段 4｜生产化（持续）

补齐端到端测试、回归测试、错误告警、备份、模型降级和限额策略；使用 Docker 或受控主机部署，定期执行依赖与安全审计。

6. 开发约束与风险清单

  • 缓存与上下文：同一会话中保持系统提示词和工具集合稳定；不要中途重建 prompt 或插入破坏角色交替的消息。
  • 核心工具成本：每个核心模型工具都会随 API 请求发送。业务/第三方能力应优先在插件、MCP 或 CLI+Skill 实现。
  • 凭据与安全：密钥只进 .env；行为配置进 config.yaml；外部 API 必须采用最小权限、输入验证和明确的审批路径。
  • 插件边界：第三方产品集成应作为独立插件仓库发布，避免把供应商特定维护负担放入核心树。
  • 前端边界：Dashboard 的主聊天体验是嵌入的 TUI，不应在 React 中另造一套聊天/输入管线；Desktop、TUI、Web 的共享协议应经 JSON-RPC 维持一致。
  • 测试策略：改动涉及配置传播、远端后端、文件/网络 I/O 或权限边界时，需要真实路径 E2E 测试；不要用枚举数量、版本字面量等“变化探测器”测试替代行为契约。
